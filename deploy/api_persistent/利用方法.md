# api_persistent 版 docker compose 利用方法

Persistence 層を「DBアクセス API への HTTP 呼び出し」に差し替えた版。
**前提条件: Blazor(Sample.Web)と DBアクセスAPI(Sample.Api)を同一コンテナで動かす。**

## 前提
- baseline / rcl / without_dip / api_persistent の複数を同時起動してはならない
    - ホスト側ポート 8080 が衝突する
- ソースルート `api_persistent/` に **Sample.Web と Sample.Api の両方**が存在すること
    - Sample.Api は Sample.sln に含めない完全独立プロジェクト(`dotnet new webapi --use-controllers`)
- `api_persistent/.dockerignore` を置くこと(bin/obj/.git/.devcontainer を除外)

## 構成(baseline との差分)

```
                    ┌─────────────────── app コンテナ ───────────────────┐
                    │                                                     │
  ブラウザ ──8080──▶│  Sample.Web (Blazor / :8080)                       │
                    │        │ HttpClient                                 │
                    │        ▼                                            │
                    │  Sample.Api (127.0.0.1:5136 ← loopback 専用)        │──1521──▶ oracle コンテナ
                    │        EF Core / Oracle                             │
                    └─────────────────────────────────────────────────────┘
```

- baseline は Sample.Web 1 本が直接 Oracle を触っていた。
- 本版は Sample.Web と Oracle の間に Sample.Api を挟む。Sample.Web は DB を知らない(HttpClient のみ)。
- 両プロセスを 1 コンテナに同居させ、`entrypoint.sh` が起動する。

## 設定キー（別キー方式）

Sample.Web と Sample.Api は **別々の設定キー**を読む。よってコンテナ共通 env に両方を置いてよい。
各プロセスは自分の読むキーだけ読み、他方のキーは無視する。

| プロセス     | 読む設定キー              | 中身                  | compose の env(`__` は `:` の代替) |
|-------------|--------------------------|----------------------|-----------------------------------|
| Sample.Web  | `ConnectionStrings:BomApi` | DBアクセスAPI の URL   | `ConnectionStrings__BomApi`       |
| Sample.Api  | `ConnectionStrings:Bom`    | Oracle 接続文字列      | `ConnectionStrings__Bom`          |

> 経緯: 当初は両者が同じキー `ConnectionStrings:Bom` を読んでいて、
> 1 コンテナ同居だと衝突した。Sample.Web 側を `BomApi` へ改名して解消。
> これにより entrypoint はプロセス別に接続情報を注入する必要がなくなり、
> 待受URL(port)の割り当てだけを担う。

## セキュリティ上の設計点

Sample.Api は **`127.0.0.1:5136` にのみ束縛**(EXPOSE もしない)。
→ 「生の DB アクセスを HTTP で晒す」面が、compose ネットワークにもホストにも一切出ない。
同一コンテナ内の Sample.Web からだけ到達できる。
（設計会話の ★要確認〔この層を別途守る必要がある〕への、最小構成での回答。）

## 初回起動

```bash
$ cd deploy/api_persistent/
$ docker compose up -d --build
```

### サンプルアプリへのアクセス URL
- http://localhost:8080/bom
- ログイン: id1 / password1

## 停止
- `docker compose stop`

## 2 回目以降の起動
- `docker compose start`

## サンプル停止・コンテナ削除
- `docker compose down`

## 動作確認・切り分け

```bash
# 2 プロセスが動いているか
$ docker compose exec app ps -ef | grep dotnet

# コンテナ内から API 単体を叩く(loopback なのでコンテナ内からのみ可)
$ docker compose exec app bash -lc 'curl -s http://127.0.0.1:5136/api/bom/rows'

# ログ(Web と Api の両方が混在して出る)
$ docker compose logs -f app
```

## メモ
- `app.UseHttpsRedirection()` は Web/Api とも HTTP のみの構成では
  「https ポートを決定できない」という警告を出すだけで、リダイレクトはしない(無害)。
  警告を消したいなら両 Program.cs から外してよい。
- Sample.Api を **別コンテナ**に分離したくなったら:
    1. `entrypoint.sh` を Web 用と Api 用に分割
    2. Api 側の束縛を `http://+:5136` に変更(loopback → 全 IF)
    3. compose に `api` サービスを追加し、`ConnectionStrings__BomApi` を `http://api:5136/` に変更
  本版は「同一コンテナ」前提のため、上記はしていない。
